# 广告投放规则与引擎机制

> 本文档定义 TeleHubX 广告投放（Campaign）的完整规则、调度算法与执行细节。
> 任何修改 Campaign Dispatch 的代码必须先看这里，否则会破坏既定行为。
>
> 最后更新：2026-05-01

---

## 一、目标与发送号

### 1.1 目标解析顺序

广告投放的目标人群按以下顺序合并并去重：

1. **客户群**（CampaignWizard Step 1 选的 customerGroupIds）
2. **手动号码**（CampaignWizard Step 1 文本框填的 targets）
3. **候选池**（如果客户群是 sourceType='candidates' 类型，已经包含了候选池数据）

去重规则：
- 电话号码按 `normalizePhone()` 后比较
- `@username` 按小写比较
- `tgUserId` 按字符串比较
- 同一目标在多个来源出现，只发一次

### 1.2 发送号筛选（智能模式）

「智能安排」账号来源会自动筛选可用号：

| 条件 | 通过 | 拒绝 |
|---|---|---|
| 角色 | `ad` / `hybrid` | `cs` |
| 状态 | `online` / `offline` | `banned` |
| 健康度 | `healthScore ≥ 60` | `< 60`（黄/红健康） |
| 隔离期 | `quarantineUntil < now()` | 还在隔离 |
| 接管状态 | 不在接管 | 在 HUMAN takeover |
| 养号天数 | `createdAt ≥ 14 天前` ⚠️ **软提示** | < 14 天会弹确认窗口但不阻止 |

**软提示规则**：账号没养满 14 天时，启动会弹「承载不足」确认弹窗告知风险，但允许租户强制启动（测试场景必备）。

### 1.3 自定义槽位模式

租户可手动选号（`accountSourceMode: manual` + `adAccountIds: []`），系统不再自动筛选，但仍会跳过：
- 接管中的账号
- 隔离期账号
- banned 账号

## 二、节奏档位

定义在 `apps/server/src/campaigns/campaign.entity.ts` 的 `PACE_LIMITS`：

| 档位 | 每号每天上限 | 时段数 | 适用场景 |
|---|---|---|---|
| **保守 (conservative)** | 20 条 | 3 时段 | 新号 / 风险敏感 |
| **平衡 (balanced)** | 30 条 | 3 时段 | 推荐默认 |
| **投放 (aggressive)** | 40 条 | 2 时段 | 成熟号 / 紧急活动 |

**硬上限：** 无论档位，每号每天**永远不能超过 40 条**（TG 私聊安全线）。

## 三、目标分配算法

### 3.1 均分（默认）

```
目标数 N = 300
可用账号数 K = 10
每号配额 quota = ceil(N / K) = 30
```

### 3.2 跨天分配

如果 `quota > 档位上限`，自动延伸到多天：

```
档位上限 dailyLimit = 20 (保守)
quota = 30
天数 days = ceil(quota / dailyLimit) = 2
分配:
  D1: 每号发 20 条
  D2: 每号发 10 条
```

### 3.3 同 IP 组互斥

> 状态：⚠️ Phase 2 实现，当前先不做

如果多个账号绑同一个住宅代理 IP（同 `proxyId` 或同 `boundIp`）：
- 同组账号不能在同一分钟发
- 组内串行：A 发完 → 等 30s → B 发

### 3.4 分配顺序

为防止"按顺序号" 全发完同一批人导致同一目标被同一号反复打：
- 用账号 id 的稳定 hash 顺序循环分目标
- 每号拿到的 30 个目标是**伪随机交错**的，不是连续 30 个

## 四、时段打散

### 4.1 时段定义

| 档位 | 时段窗口（本地时间）|
|---|---|
| 保守 (3 时段) | 09:30–11:30 / 14:00–16:30 / 18:00–20:30 |
| 平衡 (3 时段) | 09:30–11:30 / 14:00–16:30 / 18:00–20:30 |
| 投放 (2 时段) | 10:00–14:00 / 16:00–20:00 |

**全局规则：**
- 任何时段都不能跨过 09:00–21:00 本地时间窗口
- 时段之间有静默期（模拟午休/晚餐）

### 4.2 时段内分配

每号在每个时段内分到 N 条 → **高斯随机间隔**：

```
时段长度 = 120 分钟
N = 7 条
平均间隔 μ = 120 / 7 ≈ 17 分钟
标准差 σ = μ × 0.4 ≈ 7 分钟
每条间隔 = N(μ, σ)，clamp 到 [3 分钟, 60 分钟]
```

### 4.3 任务时间生成

每次发送任务的 `scheduledAt`：

```
scheduledAt = 时段起点 + 累计 Gaussian 间隔
```

调度精度到秒。多任务在同一秒不会冲突。

## 五、文案与开场白

### 5.1 来源

| 配置 | 实际数据 |
|---|---|
| `adTemplateId` (单一广告) | 从 ad_templates.variants 取所有变体 + 原文 |
| `adTemplateIds` (多广告轮换) | 多模板的 variants 合并池 |
| `messageVariants` (老字段，向后兼容) | 直接用作变体池 |
| `greetingMode = fixed/random + greetingTemplateIds` | 选中开场白的 text + variants |
| `greetingMode = none` | 不加开场白 |

### 5.2 选取规则

每次发送时：
1. **开场白**：
   - `none` → 跳过
   - `fixed` → 始终用第一条
   - `random` → 从开场白池随机抽（包括 variants）
2. **广告**：从广告变体池随机抽
3. **复用控制**：⚠️ Phase 2 实现 — 同号同变体最多复用 3 次

### 5.3 消息组装

**默认（一条合并）：**
```
[开场白]

[广告正文]
```

发送方式：单条消息发出。

> Phase 2 可选: 分两条发（先开场白 → 5-15 秒 → 正文），拟真度更高但风险翻倍。

## 六、失败处理与状态机

### 6.1 错误码处理

| 错误 | 处理 |
|---|---|
| `USER_PRIVACY_RESTRICTED` | 该目标 `dead`，跳过，不重试 |
| `PEER_ID_INVALID` | 该目标 `dead`，从客户群移除（可选） |
| `USERNAME_NOT_OCCUPIED` | 该目标 `dead` |
| `FLOOD_WAIT` | 该号暂停 N 秒，未发的任务延后 |
| `PEER_FLOOD` | 该号当天停发，明天恢复 |
| `USER_BLOCKED_BY_ADMIN` | 该号被某用户 block，跳过该目标 |
| 网络错误 | 重试 1 次，再失败标 `failed` |

### 6.2 任务状态流转

```
pending → running → succeeded
                  ↘ failed
                  ↘ canceled
```

任务级别状态由 agent 写。

### 6.3 Campaign 级别状态

```
draft → scheduled → running → completed
                            ↘ paused (用户暂停)
```

完成判定：所有子任务 (succeeded + failed + canceled) = 总任务数

## 七、进度回写

### 7.1 每次发送后

agent 端的 campaignSingle 执行器在每条发送完成后：
1. 调用 `POST /campaigns/:id/sent` 通知后端 +1
2. 后端 `campaign.sentCount++`
3. 候选池来源的目标 → 额外标记 `lead_candidates.status = 'contacted'`

### 7.2 接收回复后

bot-gateway 收到客户回复时：
1. 检查该 chatId 是否在某 campaign 的 targets 中
2. 是 → `campaign.replyCount++`

### 7.3 完成检测

每次任务状态更新时：
- 查 campaign 下未完成任务数
- 0 → `campaign.status = 'completed'`, `completedAt = now()`

## 八、安全护栏（Guardrails）

无论档位如何，以下规则永远生效：

1. **夜间保护**：09:00–21:00 之外不发送
2. **接管保护**：发送前检查目标是否被人工接管，是则跳过
3. **单号每日硬上限**：40 条（即使档位是「投放」也不会超）
4. **同号最小间隔**：≥ 60 秒（防止极端异常）
5. **租户暂停**：`tenant.status = 'suspended'` → 所有 campaigns 暂停
6. **License 失效**：`tenant.licenseExpiresAt < now()` → dispatch 拒绝

## 九、测试场景的友好性

为了让租户能在没养号 14 天的情况下测试整套流程：

1. 14 天养号是**软提示**，不阻止启动
2. 「承载不足」时按钮变为「强制启动 (承载不足)」
3. 点击弹确认窗口告知风险，确认后才发送
4. 测试场景下账号即使健康度低，仍会尝试发送（具体错误由 agent 上报）
